## 3. Implementation decisions and deviations

**D1 — 403 envelope code is `FORBIDDEN`, not `PERMISSION_DENIED` as §11 sketched.** The
pre-existing error middleware emits `FORBIDDEN` for `ForbiddenError`; reports reuse the shared
middleware instead of a report-specific code. The Flutter mapper handles `FORBIDDEN`
(`reports_error.dart`), so the user-visible behaviour matches the decision (localized "not
authorized", never a raw dump).

**D2 — 132 keys at Step E (now 135 after Human QA Fix Round 1, §10), not the §14 estimate of
~103.** Real tabs/CSV headers/KPI labels outnumbered the estimate; `status_all` (`الكل` /
`Toutes` / `All`) was added because the sales-status filter has an `all` segment. Parity across
ar/fr/en is asserted by the localization test (396 entries at Step E; 405 now).

**D3 — device filter is a free-text `TextField`, not a device picker.** Device registry does not
exist (out of scope) and inventing one would fabricate a catalogue; the field is passed through
as `device_id` and echoed in CSV filenames/filters like any other param.

**D4 — permission checks are in-screen, not route redirects; the Dashboard rail entry stays
visible.** `/` *is* the dashboard (`app_router.dart` L81: `path: '/'` → `DashboardScreen`), so a
route-level redirect would strand every authenticated user without `report_financial` in a loop
(login → `/` → redirect → …). `DashboardScreen` therefore renders the localized `dashboard-denied`
state before any money appears (§10's "no money rendered before permission resolves" holds), and
the *Reports* rail entry — a new destination — **is** gated by `canViewReports`. Deviation from
§10's "Dashboard destination becomes gated too": hiding the entry would leave `/` unreachable from
the rail for cashier sessions. Cashier behaviour: no Reports entry; Dashboard opens into the
denied state (covered by `dashboard_screen_test.dart`).

**D5 — hourly timeline's totals cell for `sales_total` is blank.** The hour bucket has no single
"sales total" that is not the sum of the rows above it; rendering `0` or a duplicate would be
wrong. Charts render only up to 48 bars (tables always render; G24 plain widgets).

**D6 — financial/suppliers CSV totals row, column 0 = `'<dateFrom> - <dateTo>'` (the "Period"
header), not `label_total`.** The CSV header for that column is *Period*; printing "Total" under a
period column would mislabel the cell. Aggregate reports keep the `total` row per §12.2; pure
detail lists (voided, slow-moving) omit it.

**D7 — chart height budget: `ReportBarChart` uses `height + 40`, callers wrap in
`SizedBox(height: 200)`.** The Cairo text engine's 1.3 line-height made the axis-label row 6 px
taller than the widget budget; `+ 34` overflowed by 2 px (test failures), `+ 40` + a 200 px
wrapper gives 160 px plot + 40 px labels with margin.

**D8 — migration 0020 also creates two PostgreSQL-only `CREATE STATISTICS` objects**
(`st_0020_sales_utc_day`, `st_0020_sale_lines_item`) with `ANALYZE`, guarded by
`dialect.name == "postgresql"` (no-op on SQLite; downgrade drops them first). Without them the
planner estimated ~1 row per group for the UTC-day `GROUP BY`, refused partial aggregation and
ran the daily/products/categories statements serially — 2.2× slower (Step D). The expressions
must match the report SQL byte-for-byte to be picked up; both are documented in the migration
docstring. Deviation note: §16.2 only specified the four btree indexes; the statistics are an
additive outcome of the Step D budget pass.

**D9 — `tests/integration/test_migrations.py` `HEAD_REV` moved from `2f6b9c4d8a31` to
`4a1e5c7b9d2f` (7 sites) and `test_single_head_is_0019` renamed to `…_0020`.** Required by Step C;
the suite runs against the dedicated `supermarket_pro_test` database (production untouched).

**D10 — three pre-existing widget tests asserted the dashboard placeholder text** and were
updated to `find.byType(DashboardScreen)`: `auth_shell_test.dart` (3), `login_button_test.dart`
(1), `pin_keyboard_test.dart` (1). The `Reports - Phase 2` placeholder had no test assertions.

**D11 — preset dropdown item keys are `reports-preset-item-<preset>`.** The original field key
pattern collided with the generic field key used by the harness; unique per-item keys keep both
lookups unambiguous.

**D12 — financial/suppliers CSV export and hourly totals follow §12.2's "export = what you
see"** — CSV is built from the exact payload on screen (no re-query), so pagination/row-cap
behaviour is shared with the table.

### A. Preset date semantics (`lib/features/reports/reports_providers.dart`)

| Preset | dateFrom | dateTo | Rule |
|---|---|---|---|
| `today` | 2026-10-01 | 2026-10-01 | local calendar day |
| `yesterday` | 2026-09-30 | 2026-09-30 | today − 1 |
| `last_7_days` | 2026-09-25 | 2026-10-01 | today − 6 … today (inclusive) |

### A. Central tone system (`lib/features/reports/report_tones.dart`, new)

Widgets never hardcode hues — they name a `ReportMetricTone` and resolve it through the **active
`ThemeData`** (`resolveReportTone`):

| Tone | Meaning | Light accent | Dark/Grey accent | Icon |
|---|---|---|---|---|
| `sales` | revenue family | `colorScheme.primary` (blue) | `colorScheme.primary` | `point_of_sale_outlined` |
| `profit` | gross/net profit, margin | `0xFF2E7D32` (green 800) | `0xFF66BB6A` (green 300) | `trending_up` |
| `expense` | expenses | `0xFFC62828` (red 800) | `0xFFEF5350` (red 300) | `receipt_long_outlined` |
| `returnValue` | returns | `0xFFEF6C00` (orange 800) | `0xFFFFB74D` (orange 300) | `assignment_return_outlined` |
| `debt` | receivables / payables | `0xFFD84315` (deep orange 800) | `0xFFFF8A65` (300) | `request_quote_outlined` |
| `cost` | COGS / purchases | `0xFF9C6400` (amber 800) | `0xFFFFD54F` (amber 300) | `shopping_bag_outlined` |
| `inventory` | stock / products | `0xFF6A1B9A` (purple 800) | `0xFFCE93D8` (purple 300) | `warehouse_outlined` |
| `documents` | invoice / document counts | `0xFF00838F` (cyan 800) | `0xFF4DD0E1` (cyan 300) | `receipt_outlined` |

- **800-level on light, 300-level on dark** (≈4.5:1 on white where practical, ≥3:1 for large
  bold numbers); Grey is `Brightness.dark`, so it resolves the dark palette.
- Helpers: `reportKpiTone(labelKey)` (KPI label → tone; discounts/unknown = neutral `null`),
  `reportColumnTone(labelKey)` (only profit columns → green sign-aware, returns columns →
  orange — tables never become a rainbow), `reportToneIcon` (one restrained icon per tone).
- **`reportValueColor` rules:** a value starting with `-` → expense red regardless of tone (sign
  check only; the server string is never reformatted); positive profit → green; expense and
  sales values stay **neutral** (the accent lives on the icon — a screen of red numbers would
  read as errors, blue numbers would fight profit greens); return/debt/cost values take their
  tone accent; `null` tone → default text color.

### B. KPI cards (`ReportKpiTile` in `report_widgets.dart`)
